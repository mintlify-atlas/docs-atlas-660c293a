## Test Structure

The K6 performance test is located at `tests/performance/performanceTest.js` and follows K6's standard structure:

1. **Imports**: Load K6 modules
2. **Configuration**: Define test scenarios and parameters
3. **Test function**: The main function executed by virtual users
4. **Checks**: Validations to verify performance criteria

## Environment Configuration

The test uses environment variables for configuration:

```javascript
const url_api = __ENV.HOST_PAGE
const token = __ENV.QA_PASSWORD
```

- **HOST_PAGE**: The base URL of the API being tested
- **QA_PASSWORD**: Authorization token for authenticated requests

These variables are loaded from your `.env` file when running tests.

## Test Scenario: Constant Arrival Rate

The test implements a constant-arrival-rate scenario, which maintains a steady request rate regardless of system performance:

```javascript
export const options = {
  scenarios: {
    constant_request_rate: {
      executor: 'constant-arrival-rate',
      rate: 20,              // 20 solicitudes...
      timeUnit: '1s',        // ...por cada segundo (RPS)
      duration: '30s',       // Durante 30 segundos
      preAllocatedVUs: 10,   // Usuarios virtuales iniciales
      maxVUs: 50,            // Máximo de usuarios si el sistema tarda en responder
    },
  },
};
```

### Configuration Parameters

<ParamField path="executor" type="string" default="constant-arrival-rate">
  The execution pattern - maintains a constant rate of iterations
</ParamField>

<ParamField path="rate" type="number" default="20">
  Number of requests to send per time unit (20 requests per second)
</ParamField>

<ParamField path="timeUnit" type="string" default="1s">
  Time window for the rate - typically '1s' for requests per second
</ParamField>

<ParamField path="duration" type="string" default="30s">
  Total test duration - how long to maintain the constant rate
</ParamField>

<ParamField path="preAllocatedVUs" type="number" default="10">
  Initial number of virtual users allocated at test start
</ParamField>

<ParamField path="maxVUs" type="number" default="50">
  Maximum virtual users K6 can spin up if response times increase
</ParamField>

### How It Works

The constant-arrival-rate executor ensures exactly 20 requests start every second:

- If responses are fast, fewer VUs are needed
- If responses slow down, K6 adds more VUs (up to maxVUs) to maintain the rate
- This simulates realistic load where users arrive at a steady pace
- The test runs for 30 seconds, generating approximately 600 total requests

## Test Function

The main test function executes for each virtual user iteration:

```javascript
export default function () {
  // Sustituyo la URL por la de tu API
  const url = `${url_api}/V1/invoices?page=1`;
  
  const params = {
    headers: {
      'Authorization': token,
      'Content-Type': 'application/json',
      // Agrego mis headers, token de autenticación si son necesarios
    },
  };

  const res = http.get(url, params);

  // Validación básica del estado 200
  check(res, {
    'status es 200': (r) => r.status === 200,
    'tiempo de respuesta < 500ms': (r) => r.timings.duration < 500,
  });
}
```

### What the Test Does

1. **Constructs URL**: Targets the `/V1/invoices?page=1` endpoint
2. **Sets headers**: Includes authorization token and content type
3. **Sends GET request**: Retrieves the first page of invoices
4. **Validates response**: Checks status code and response time

### Performance Checks

The test includes two critical validations:

<AccordionGroup>
  <Accordion title="Status Code Check">
    ```javascript
    'status es 200': (r) => r.status === 200
    ```
    
    Verifies that the API returns a successful HTTP 200 response. Failed checks indicate:
    - Authentication failures (401/403)
    - Server errors (500+)
    - Not found errors (404)
  </Accordion>

  <Accordion title="Response Time Check">
    ```javascript
    'tiempo de respuesta < 500ms': (r) => r.timings.duration < 500
    ```
    
    Ensures responses complete within 500ms. This represents the SLA requirement. Violations indicate:
    - Database query performance issues
    - Resource contention under load
    - Network latency problems
  </Accordion>
</AccordionGroup>

## Running the Tests

Execute performance tests using the npm script:

```bash
npm run test:performance
```

This command runs:

```bash
dotenv -- k6 run tests/performance/performanceTest.js
```

The `dotenv` wrapper loads environment variables from your `.env` file before executing K6.

<ResponseField name="vus" type="count">

</ResponseField>

## Interpreting Performance

### Healthy Results ✓

- **Checks**: 100% pass rate
- **http_req_duration p(95)**: < 500ms (meets SLA)
- **http_req_failed**: 0%
- **vus**: Low and stable (system handles load efficiently)

### Warning Signs ⚠️

- **Checks**: < 100% (some requests failing SLA)
- **http_req_duration**: Increasing over time
- **vus**: Approaching maxVUs (system struggling to keep up)

### Critical Issues ✗

- **http_req_failed**: > 0% (errors occurring)
- **http_req_duration p(95)**: > 500ms (SLA violations)
- **vus**: Hitting maxVUs limit (cannot maintain target rate)

<Warning>
If the test hits `maxVUs` (50 virtual users) and still cannot maintain 20 RPS, the system cannot handle the target load. This indicates a serious performance bottleneck.
</Warning>

## Customizing the Test

Modify test parameters to match your needs:

### Increase Load

```javascript
rate: 50,              // 50 requests per second
maxVUs: 100,           // Allow more concurrent users
```

### Longer Duration

```javascript
duration: '5m',        // 5 minute sustained test
```

### Different Endpoint

```javascript
const url = `${url_api}/V1/customers?page=1`;
```

### Additional Checks

```javascript
check(res, {
  'status es 200': (r) => r.status === 200,
  'tiempo de respuesta < 500ms': (r) => r.timings.duration < 500,
  'body contiene datos': (r) => r.json().data !== undefined,
  'respuesta no vacía': (r) => r.json().data.length > 0,
});
```
